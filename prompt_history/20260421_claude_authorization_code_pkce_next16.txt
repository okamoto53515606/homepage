結論として、現在の方式は「即危険で使えない」までは言いませんが、認証方式としては少し古く、いくつか明確な改善ポイントがあります。現実装は blueprint_v2.md の記述と少しズレていて、実際には `CLIENT_SECRET` を使うサーバー側コード交換ではなく、auth-provider.tsx でブラウザが Google に飛び、auth-provider.tsx の `response_type=id_token` で `id_token` を受け取り、route.ts で署名検証して自前セッション Cookie に変換しています。なので、この方式では `CLIENT_SECRET` は本質的に不要です。逆に言うと、設計書にある「`GOOGLE_CLIENT_SECRET` を Secrets Manager で管理」は現状コードと整合していません。

セキュリティ上の懸念は主に4つです。1つ目は implicit に近い front-channel フローなので、`id_token` がブラウザ側に露出することです。URL フラグメントなのでサーバーログには通常乗りませんが、ブラウザ拡張、XSS、クライアント側の不正スクリプトには見えます。2つ目は `nonce` を生成しているのに検証していないことです。auth-provider.tsx で `google_auth_nonce` を保存していますが、コールバック処理では `state` しか見ておらず、route.ts でも `aud` と `iss` は検証していても `nonce` は検証していません。OIDC では implicit/id_token フローでの `nonce` 検証は重要です。3つ目は `state` と `nonce` の生成に `Math.random()` を使っていることです。auth-provider.tsx の用途なら `crypto.getRandomValues()` か `crypto.randomUUID()` を使うべきです。4つ目は、今の方式自体が現在の推奨から外れ気味なことです。一般論としては SPA/ブラウザアプリは Authorization Code + PKCE が推奨で、implicit は後方互換としては残っていても新規採用の第一候補ではありません。外部根拠としては Google の client-side OAuth 文書は依然 client-side flow を案内していますが、Microsoft や Auth0、OAuth/OIDC 周辺の現行ガイダンスは PKCE を推奨しています。たとえば [Google Developers](https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow)、[OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)、[Microsoft Learn](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)、[Auth0](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow-with-pkce) が参考になります。

ただし、良い点もあります。route.ts で Google の JWKS による署名検証、issuer 検証、audience 検証をしていて、受け取った `id_token` をそのままアプリ認可に使わず、HTTP-only の自前セッション Cookie に落としているのは妥当です。なので現状評価は「致命的ではないが、強く改善推奨」です。優先順位は、1. `nonce` 検証を入れる、2. `Math.random()` をやめる、3. 設計書と実装のズレを直す、4. 可能なら Authorization Code + PKCE へ移行、です。`CLIENT_SECRET` を本当に使いたいなら、その時点で方式自体を server-side code exchange に変える必要があります。今の方式のまま `CLIENT_SECRET` だけ追加してもセキュリティはほぼ上がりません。

1. 最小修正で `nonce` 検証と安全な乱数生成だけ入れる  
2. 設計書を現実装に合わせて整理する  
3. Google ログインを Authorization Code + PKCE 前提で組み直す
