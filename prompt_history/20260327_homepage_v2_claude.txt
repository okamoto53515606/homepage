## 全体的な方向性：良い判断

**AWS移行は正しい選択**です。理由：

1. **CDN問題が解決する** - Firebase App Hostingの「ミドルウェア経由ルートはキャッシュされない」制約がCloudFrontには存在しない
2. **CDKでのIaC** - AIエージェントが状況把握しやすく、非エンジニア向けの「鍵を渡して自動構築」が実現可能
3. **vendor lockの軽減** - 開発環境もバックエンドもGoogle依存から脱却

## 3つの重要な方向性判断

### 1. 静的生成 vs ISR（推奨：ISR）

blueprint_v2では「静的ファイル + CDN」と書かれていますが、CloudFrontなら**ISR（Incremental Static Regeneration）+ Lambda@Edge**の方が現実的：

| 方式 | メリット | デメリット |
|------|---------|----------|
| 完全静的 | シンプル、爆速 | 記事更新時に全ページ再ビルド |
| **ISR + CloudFront** | 動的追加OK、キャッシュ可 | Lambda@Edgeが必要 |

Firebaseで断念した理由（ミドルウェア問題）がAWSでは消えるので、**ISR路線を再検討する価値あり**。

### 2. 管理画面の完全分離（推奨：分離しつつシンプルに）

方向性は良いが、**別ドメイン+Cognito**は実装コストが高い。代替案：
- 同一ドメインの `/admin/*` をCloudFront Functionsで**IPホワイトリスト + Basic認証**で保護
- これだけでネットワークレベルの攻撃は防げる

Cognitoは将来の「組織向け拡張」まで温存でOK。

### 3. データ移行（Firestore → ?）

blueprint_v2ではDB選定が未記載。選択肢：

| 選択肢 | 向いているケース |
|--------|-----------------|
| **DynamoDB** | CDKと相性◎、サーバーレス |
| **Firestore継続** | 移行コスト最小、Google依存は残る |
| **PlanetScale/Neon** | RDBが欲しい場合 |

個人メディア規模なら**DynamoDB + CDK**がおすすめ。AIがスキーマを把握しやすい。

### メリット（v2に適している理由）

| 観点 | 評価 |
|------|------|
| **CloudFrontの自由度** | ✅ OAC + Lambda@Edgeで細かく制御可能。Firebase App Hostingの「ミドルウェア問題」が存在しない |
| **Next.jsの互換性** | ✅ `output: "standalone"` + Lambda Web Adapter で App Router/SSR/ISR が動作 |
| **デプロイの切り戻し** | ✅ ECRのイメージタグで簡単にロールバック可能 |
| **CDK統合** | ✅ `cdk-nextjs` コンストラクトも存在。自前で組んでも良い |

### 注意点

| 課題 | 対策 |
|------|------|
| **コールドスタート** | メモリ1024MB以上、ARM64推奨。Provisioned Concurrencyは高コストなので最初は不要 |
| **2025年8月のINIT課金変更** | コールドスタートのコストが上がった（$0.80 → $17.80 / 100万回程度）。個人メディア規模なら影響小 |
| **Lambda@Edge (us-east-1)** | POST/PUT時のSigV4署名用。記事の通り必須 |
| **静的ファイル分離** | 必須ではないが、S3に分けた方がLambdaパッケージが軽量化 |

### 選択肢の比較

| 方式 | 複雑度 | CDK連携 | おすすめ度 |
|------|--------|---------|-----------|
| **Lambda Web Adapter（記事の方式）** | 中 | 自前で組む | ✅ 良い |
| **cdk-nextjs コンストラクト** | 低 | 公式提供 | ✅ 検討の価値あり |
| SST | 低〜中 | SST独自 | ⚠️ ハマりそうなら避けて正解 |
| Amplify | 低 | Amplify独自 | ❌ ブラックボックス |
| OpenNext | 中〜高 | 要自前構築 | ⚠️ 複雑 |

## SST/OpenNext vs Lambda Web Adapter

| 観点 | SST/OpenNext | Lambda Web Adapter |
|------|-------------|-------------------|
| **内部構造** | Next.jsビルド出力を独自形式に変換 | 変換なし。Dockerイメージをそのまま動かす |
| **生成されるリソース** | 複数Lambda（Server, ImageOptimization, Revalidation等） | 1つのLambda + S3 |
| **デバッグ** | 変換後の動作がローカルと異なる可能性 | ローカルのDockerと同じ動作 |
| **Next.jsバージョン追従** | OpenNextがNext.jsの変更に追従する必要あり | Next.js側の変更に影響されにくい |
| **ブラックボックス度** | 中〜高（変換処理が複雑） | 低（Dockerfileに数行追加するだけ） |
| **AIエージェントの理解** | 難しい | 容易 |

## OpenNextの「透明性が低い」具体例

1. **変換処理**: OpenNextはNext.jsの.next出力を解析して、AWS Lambda用に再構成する。この変換ロジックがブラックボックス
2. **ISR/キャッシュ**: OpenNextは独自のキャッシュ機構（DynamoDB/S3）を使う。Next.js標準と微妙に異なる挙動になることがある
3. **エラー時の調査**: 「OpenNextの変換が悪いのか、Next.jsの問題か、AWSの問題か」の切り分けが難しい

## Lambda Web Adapterが透明な理由

```dockerfile
# これだけ
FROM node:22-slim
COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:0.8.4 /lambda-adapter /opt/extensions/lambda-adapter
ENV PORT=3000
ADD .next/standalone/ /var/task
CMD ["node", "server.js"]
```

- **ローカルと本番が同じ**: Dockerで動くものがそのままLambdaで動く
- **問題の切り分けが容易**: Next.jsの問題か、Dockerの問題か、Lambdaの問題かが明確
- **AIエージェントが把握しやすい**: 「Dockerコンテナ + Lambda拡張機能」という単純な構造
