## 原因

`generate/route.ts` で `processGeneration()` を **`await` せずに** 起動しています：

```ts
// await しない = fire & forget
processGeneration(jobId, { ... }).catch(...)
return NextResponse.json({ jobId })  // ← すぐレスポンスを返す
```

**Next.js on Lambda では、レスポンスを返した時点で実行コンテキストがフリーズします。** バックグラウンドの `processGeneration()` は「止まった状態」になり、再び動くのは**同じ Lambda インスタンスに次のリクエストが来たとき**だけです。

### 実際に起きていること

1. `POST /api/admin/articles/generate` → `processGeneration` 開始 → 即 `jobId` を返してフリーズ
2. クライアントが `GET /api/admin/jobs/{jobId}` をポーリング → **このリクエストが同じインスタンスに当たると** `processGeneration` が少し進む
3. ポーリングが別インスタンスに振られると元のインスタンスは永久にフリーズしたまま
4. 運良く同インスタンスで処理が進めば記事はDBに保存される（`PutCommand` まで完走）
5. しかし `completeJob()` の実行前にまたフリーズ → ジョブは永久に `processing` のまま
6. クライアントは120回ポーリングしても `completed` を検出できず→タイムアウトメッセージ

**記事は保存されるがジョブステータスが `processing` のまま**というのが典型症状で、おそらくDynamoDBのジョブレコードを確認すると `status: "processing"` になっているはずです。

`processGeneration` を `await` する（= CloudFront の60秒タイムアウトと正面から戦う）か、`afterCallback`/`waitUntil` を使うか、もしくは別途SQS＋別Lambdaに切り出す、などが選択肢になります。一番手軽なのは `await` に戻して CloudFront タイムアウトをオフにする方法ですが、設計上の変更が必要です。修正しますか？

## `processGeneration()` の実体

```ts
processGeneration(jobId, { ... }).catch(...) // awaitしない
return NextResponse.json({ jobId })          // ← ハンドラ終了
```

これは **OS レベルのサブプロセスではなく、同じ Node.js イベントループ上の Promise** です。

Lambda のハンドラが `return` した瞬間、Lambda ランタイムは**実行コンテキスト全体（イベントループ含む）をフリーズ**します。未完了の Promise も一緒に止まります。15分タイムアウトは「1回のリクエスト処理の上限」であり、バックグラウンド Promise の生存時間ではありません。

## なぜ今うまく動いているか（推測）

クライアントのポーリング（3秒ごとの GET）が**偶然同じ warm インスタンスに当たる**たびに、フリーズしていた Promise が解凍されて少し進む。これを繰り返して最終的に `PutCommand` まで完走しています。

```
POST → Lambda A 起動 → jobId 返却 → フリーズ
GET (poll 1) → Lambda A 解凍 → Gemini 処理が進む → フリーズ
GET (poll 2) → Lambda A 解凍 → さらに進む → フリーズ
...
GET (poll N) → Lambda A 解凍 → PutCommand 完了 → フリーズ（completeJobは未完走の場合も）
```

ポーリングが事実上「心拍」として機能しているため安定して動いている、という状況です。
