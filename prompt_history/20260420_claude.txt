## 2026/4/20 コメントへの意見

### 1. admin ロール参照の削除

> adminロールを参照するコードは削除。管理画面は別認証になるので、firebase authのカスタムクレーム（adminロール）はなくなる。

**賛成です。** Cognito で管理者認証を分離する設計であれば、`user.role === 'admin'` のような判定は不要になります。管理画面へのリンクは middleware での Cognito JWT 検証に一元化するのが正しいです。ただし、ヘッダーの「管理画面」リンクの表示制御をどうするかは要検討です（Cognito ログイン済みかどうかをクライアントで判定する手段が必要）。

### 2. 日付表示の修正（更新日 → 公開日）

> 記事一覧と記事詳細の日付は更新日でなく、公開日（dbの作成日でよい）

**理解しました。** `article-card.tsx` と `articles/[slug]/page.tsx` の表示ラベル・値の変更が必要です。これは 10.3 に記載済みの方針と一致しています。

### 3. Google ログイン / Stripe パラメータの取得元分岐

> 本番環境はシークレットマネジャーから取得し、開発環境時（ローカル起動）は環境変数から取得

**実装方針の質問:**
- 環境判定は何で行う想定ですか？ `NODE_ENV`、それとも専用の環境変数（例: `APP_ENV=production`）？Lambda 上では `NODE_ENV=production` になるので、それで分岐するのが自然ですが、`next build` 時も `NODE_ENV=production` になる点に注意が必要です。
- `GOOGLE_CLIENT_SECRET` も Secrets Manager に入れる想定ですか？ `NEXT_PUBLIC_GOOGLE_CLIENT_ID` はクライアント公開値なので Secrets Manager に入れる必要はないと思いますが、blueprint_v2.md の 4.9 では両方 Secrets Manager に保存する記載になっています。

### 4. AI 記事生成の非同期化（CloudFront 60 秒タイムアウト問題）

> Cloudfrontのタイムアウトは60秒だが、Gemini AIによる記事の作成/修正は1分以上の時間がかかる。非同期にして最大15分ポーリングしたい。

**これは重要な課題です。** 提案する実装パターン:

```
POST /api/admin/articles/generate → ジョブIDを即座に返す（DynamoDB に status=processing で保存）
                                     ↓ Lambda で AI 処理を継続
GET /api/admin/articles/jobs/{id} → ポーリングで完了確認
```

**懸念点:**
- CloudFront のタイムアウトは Origin Response Timeout（デフォルト 30 秒、最大 60 秒）です。Lambda 側で 15 分かかっても、**CloudFront が 60 秒で切断**します。なので非同期パターンは必須です。
- ただし、`/api/admin/*` は `CachingDisabled` に設定されているので、CloudFront の Origin Response Timeout を最大 60 秒に設定すれば、60 秒以内に「ジョブ受付」レスポンスを返すだけなら問題ありません。
- もう一つの選択肢: `/admin/*` パスは CloudFront を経由しないで、Lambda Function URL に直接アクセスさせる構成も考えられます（WAF + Cognito で保護されていれば安全）。

### 5. ドメイン取得の自動化（setup2b）

> AWSでの新規ドメイン取得を前提とし、ドメイン取得から自動化したい

**注意点:** Route 53 のドメイン登録（`RegisterDomain`）は CDK でサポートされていません。AWS SDK を直接呼ぶ必要があります。また、ドメイン登録は **連絡先情報（名前・住所・電話番号）** の入力が必要で、完全自動化はユーザー入力ステップが伴います。TLD によっては登録完了まで数日かかることもあります。

実装の仕組みは以下の通りです。

**新規プロセス（CLI）は立ち上げていません。** Node.js の非同期 Promise を `await しない`（fire-and-forget）パターンです。

```typescript
// ジョブを DynamoDB に作成し、即座に jobId を返す（ここまで数百ms）
const jobId = await createJob('generate');

// バックグラウンドで AI 処理を実行（await しない）
processGeneration(jobId, params).catch(error => {
  logger.error(`バックグラウンド生成エラー:`, error);
});

// CloudFront の 60 秒タイムアウト前にレスポンスを返す
return NextResponse.json({ status: 'accepted', jobId });
```

**流れ:**
1. POST リクエスト → DynamoDB に `status: 'processing'` のジョブ作成 → **即座に `jobId` を返す**（1秒以内）
2. `processGeneration()` は `await` されないため、HTTP レスポンス送信後も **同じ Lambda プロセス内**で実行が継続
3. AI 処理完了 → `completeJob(jobId, result)` で DynamoDB のジョブを `completed` に更新
4. クライアントは `GET /api/admin/jobs/{jobId}` をポーリングして結果を取得

**タイムアウト回避の仕組み:**
- CloudFront の 60 秒制限は **HTTP レスポンス**に対するもの → 即座に返すので回避できる
- Lambda 自体のタイムアウト（最大 15 分）内に AI 処理が完了すれば OK
- Lambda は HTTP レスポンスを返した後も、イベントループに未完了の Promise がある限りプロセスは生きている

**注意点:** Lambda の設定によっては、レスポンス送信後にプロセスがフリーズされる可能性があります（`context.callbackWaitsForEmptyEventLoop` 相当）。Lambda Web Adapter や standalone モードでの動作確認が必要です。
