## ZAP の動かし方（3 つの選択肢）

| 方式 | 所要時間 | カバレッジ | 向き |
|---|---|---|---|
| **A. ZAP Baseline Scan**（受動スキャンのみ、攻撃送信なし） | 5〜10 分 | ヘッダ / Cookie / CSP / mixed content など低リスク項目 | **初回・CI 組み込み向き** |
| **B. ZAP Full Scan**（能動攻撃: SQLi / XSS / Path Traversal 等を実送信） | 30〜120 分 | OWASP Top 10 相当 | 本格的な脆弱性確認 |
| **C. ZAP API Scan**（OpenAPI 定義を読ませて API を集中スキャン） | 10〜30 分 | API 単体の認証 / 入力検証 | API がメインのプロジェクト向き |

最初は **A → B の順で 2 段階**が定番です。Aは安全（攻撃トラフィックを送らない）なので CI 化候補、B は手動運用前提。

1. ブラウザで `https://test.okamomedia.tokyo/admin` にログイン
2. DevTools → Application → Cookies → `session`（JWT が入っている cookie 名）の値をコピー
3. Full Scan を Cookie 付きで実行:

```bash

  -t zaproxy/zap-stable zap-full-scan.py \
  -t https://test.okamomedia.tokyo/ \
  -r full-report.html \
  -J full-report.json \
  -z "-config replacer.full_list(0).description=session \
      -config replacer.full_list(0).enabled=true \
      -config replacer.full_list(0).matchtype=REQ_HEADER \
      -config replacer.full_list(0).matchstr=Cookie \
      -config replacer.full_list(0).regex=false \
```

（Replacer で全リクエストに Cookie を強制注入する手）

## A をスキップしていいか？

A（Baseline）は B（Full）の**上位互換ではなく検出ターゲットが違う**ので、本来は両方やる価値があります。

| 検出項目 | A (Baseline) | B (Full) |
|---|---|---|
| HTTP セキュリティヘッダ不足（CSP / HSTS / X-Frame-Options） | ✓ | ✓ |
| Cookie 属性（Secure / HttpOnly / SameSite） | ✓ | ✓ |
| 情報漏洩（Server バナー、コメント内パス） | ✓ | ✓ |
| SQLi / XSS / Path Traversal / SSRF（攻撃送信） | ✗ | ✓ |
| CSRF / Open Redirect | △ | ✓ |

つまり **B は A の検出項目を全部含む**（受動スキャナは Full Scan でも常時動いている）ので、**A をスキップして B からで OK** です。WAF の有無とは関係なく「B だけで A の結果も得られる」ので、時間効率としても妥当な選択です。

## B → C の順序について

逆順（**C → B**）を推奨します。理由:

1. **C（API Scan）は OpenAPI 定義から URL / パラメータ / 認証スキームを ZAP に直接渡す**ので、B のクロールで見つけられない API も網羅できる
2. C で API レイヤを先に潰しておくと、B のフルスキャンは**画面（HTML / RSC / 静的アセット）に集中**でき、結果ノイズが減る
3. B のフルスキャンは時間がかかる（30〜120 分）ので、C で先に「明らかな低層バグ」を取っておく方が手戻りが少ない

ただし本プロジェクトには**現状 OpenAPI 定義がありません**（Route Handler の手書き）。C をやるには定義を作る必要があり、これがそこそこ手間です。

## OpenAPI 定義の作り方の選択肢

| 案 | 工数 | 精度 | メンテ |
|---|---|---|---|
| **C-1. ZAP に手動 URL リスト**を渡す（簡易 OpenAPI 風 YAML を私が書く） | 小（30 分） | 中 | 手動 |
| **C-2. 既存 Route Handler を grep して半自動生成** | 中（私が一回書けば終わる） | 高 | 半手動 |
| **C-3. Zod スキーマから OpenAPI 自動生成**（`zod-to-openapi` 等を導入） | 大（実装変更必要） | 最高 | 自動 |

DAST 目的なら **C-1 か C-2 で十分**。CI 化やドキュメント化まで視野に入れるなら C-3。

## なぜ False Positive と断言できるか

本プロジェクトは **DynamoDB (NoSQL) のみ**を使っており、SQL データベースは一切使っていません。SQL インジェクション攻撃は SQL クエリ文字列の組み立てがある場合にのみ成立するため、アーキテクチャ的に発生不可能です。

ZAP の SQLi 検出 (Plugin 40018) は「Boolean-based」方式で、`AND 1=1` と `AND 1=2` を注入してレスポンスのサイズ/内容が変わるかで判定しています。レスポンスが変わる理由が SQL 以外でも (バリデーションエラー、認証エラー、Cognito リダイレクト URL の違い等) 警告が出る既知の弱点です。

## 各エンドポイントの実際の挙動

| エンドポイント | レスポンス差の原因 |
|---|---|
| `DELETE /api/admin/articles?id=...` | DynamoDB `DeleteCommand` (KeyCondition 完全一致) — id 文字列の中身に関わらず該当なしなら成功扱い。差分は ZAP の認証状態の差 |
| `DELETE /api/admin/comments?id=&articleId=...` | DynamoDB `DeleteCommand` 同上 |
| `GET /api/admin/auth/callback?code=...` | Cognito Token Endpoint へ渡して検証失敗 → エラーページにリダイレクト。`code` の長さで URL 長が変わり差分検出 |
| `GET /api/auth/google/callback?code=...&state=...` | state 不一致で 400、PKCE 検証で別エラー → レスポンス差 |
| `GET /api/auth/google/start?returnTo=...` | `returnTo` の中身がリダイレクト URL に含まれるため必ずレスポンスサイズが変わる (これは設計通り) |
| `GET /auth/callback?error=...` | `error` がページ HTML 内に表示されるため当然サイズ差が出る |

いずれも SQL を組み立てていないので、`'` や `--` を渡しても SQL として評価されません。
