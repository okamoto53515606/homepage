## ③ Firebase Auth `uid` → `google_uid`(sub) への置き換え

**賛成ですが、移行時に注意点があります。**

移行方針案：
- `google_uid` がある → そのまま新PKとして使用
- `google_uid` がない → 移行対象外（v2では新規登録してもらう方針とblueprint_v2.mdに記載あり）

## ④ Stripe連携パラメータの格納先: DynamoDB vs Secrets Manager

**Secrets Manager を推奨します。** 理由：

| 観点 | DynamoDB + KMS暗号化 | Secrets Manager |
|------|---------------------|----------------|
| **実装コスト** | KMS暗号化/復号のコードを自前実装 | SDKで `getSecretValue()` / `putSecretValue()` だけ |
| **セキュリティ** | 暗号化ロジックのバグリスク | AWS側で保証 |
| **監査** | CloudTrail + 自前ログ | CloudTrailで自動記録 |
| **ローテーション** | 自前実装 | 組み込み機能あり |
| **コスト** | DynamoDB分のみ | ~$0.40/月/シークレット（4つで$1.60/月） |
| **管理画面連携** | 直接read/write | API経由でread/write |

管理画面からは `/api/admin/stripe-config` のようなエンドポイントを用意し、Lambda が Secrets Manager に read/write する構成にすれば、管理画面から設定変更も可能です。CDK で Secrets Manager のリソースを定義し、Lambda に `secretsmanager:GetSecretValue` / `PutSecretValue` の IAM 権限を付与すれば完結します。

格納するシークレット：
- `STRIPE_SECRET_KEY`
- `STRIPE_WEBHOOK_SECRET`
- `NEXT_PUBLIC_STRIPE_PUBLIC_KEY`（これは公開キーなので settings テーブルでも可）
- `STRIPE_TAX_RATES`（オプション）

→ 1つの Secrets Manager シークレットに JSON 形式でまとめるのが管理しやすいです。

## DynamoDB テーブル設計の方針

**別テーブル方式（テーブル分離）** を推奨します。Single Table Design は DynamoDB の上級テクニックですが、このプロジェクトの規模・アクセスパターンなら別テーブルの方が：
- 設計がわかりやすい
- CDK の定義がシンプル
- 将来の変更が容易

## GCS → S3 メディア移行方針

### 現状整理

| 項目 | 値 |
|------|-----|
| GCS バケット | `studio-4200137858-cfe20.firebasestorage.app` |
| 旧 URL パターン | `https://storage.googleapis.com/{bucket}/articles/{uid}/{timestamp}-{filename}` |
| 記事内の参照 | content（マークダウン本文）+ imageAssets 配列 |
| ファイル総数 | 131 assets（24記事） |
| content 内 URL | 一部に `?v20250303` 等のクエリパラメータ付き |

### S3 キー設計

```
旧: articles/{uid}/{timestamp}-{filename}
新: articles/{articleId}/{timestamp}-{filename}
```

**uid → articleId に変更する理由:**
- v2 では Firebase Auth uid が廃止される
- 記事に紐づくファイルなので articleId が自然
- ただし `{uid}` 部分は全記事で同一（管理者1人）なので、フラットに `articles/{articleId}/` でも良い

**代替案: パスをそのまま維持する:**
- `articles/{uid}/{timestamp}-{filename}` のまま S3 にコピー
- URL 書き換えがドメイン部分だけで済むので最もシンプル

### 新 URL（CloudFront 経由）

```
旧: https://storage.googleapis.com/studio-4200137858-cfe20.firebasestorage.app/articles/8L047bk.../1774353168022-hat_q.png
新: https://{cloudfront-domain}/media/articles/8L047bk.../1774353168022-hat_q.png
```

CloudFront の Behavior で `/media/*` → S3 バケットにルーティング。media プレフィックスで静的ファイルと SSR を分離。

### URL マッピングルール

```
置換対象: https://storage.googleapis.com/studio-4200137858-cfe20.firebasestorage.app/
置換先:   https://{cloudfront-domain}/media/
```

- content 内の `?v20250303` 等のクエリパラメータは除去（CloudFront キャッシュ互換）
- imageAssets の url も同様に置換

### 移行スクリプトの処理

1. **GCS → S3 ファイルコピー**: GCS からダウンロード → S3 にアップロード（パス維持）

GitHub Copilot: ### 1. `/media/*` → S3, `/*` → Lambda（同一 CF）

問題なくできます。CDK で `additionalBehaviors` を追加するだけ:

```typescript
const distribution = new cloudfront.Distribution(this, 'MediaDistribution', {
  defaultBehavior: {
    origin: lambdaFunctionUrlOrigin,  // /* → Lambda
    ...
  },
  additionalBehaviors: {
    '/media/*': {
      origin: s3Origin,  // /media/* → S3
      cachePolicy: cloudfront.CachePolicy.CACHING_OPTIMIZED,
      ...
    },
  },
});
```

CloudFront はパスの長いものを優先マッチするので、`/media/*` が先に評価され、それ以外が `/*` に流れます。現在のディストリビューションをそのまま拡張可能。

### 2. `/admin/*` → 別 Lambda（別 Next.js アプリ）

**やりすぎだと思います。** 理由:

- **認証だけが違う**（Cognito vs Google OAuth）。ビジネスロジック（記事 CRUD、DynamoDB アクセス）は共通コードが多い
- 別アプリにすると data.ts, `src/lib/dynamodb.ts` 等のコアライブラリが **2 箇所で重複管理** になる
- Next.js の middleware で `/admin/*` だけ Cognito 認証チェックをかければ、**1 アプリ内で分離可能**
- デプロイ・CI/CD も 1 つで済む

**推奨:** 1 つの Next.js アプリ内で middleware による認証分岐:

```
/admin/*  → middleware で Cognito JWT 検証
/*        → middleware で Google OAuth セッション検証（既存）
/media/*  → CloudFront が S3 に直接ルーティング（Lambda に到達しない）
```

別アプリが justified になるのは、管理画面が独自 UI フレームワークを使う・チーム別開発する等のケースですが、今回は該当しないかと。
