## 1. setup1b で独自ドメイン/証明書が剥がれる件 → 賛成。実装方針も妥当

提案（証明書ARN と CLOUDFRONT_DOMAIN を env で CDK に渡す）は筋が良いです。infra-stack.ts は既に `process.env.CLOUDFRONT_DOMAIN` を読む箇所（L452）が存在しており、Distribution 側に同じ仕組みを追加するだけで済みます。

### 推奨インターフェース

.env に2つだけ追加：
- `CUSTOM_DOMAIN`（例: `www.okamomedia.tokyo`）
- `CUSTOM_DOMAIN_CERT_ARN`（us-east-1 の ACM ARN）

CDK 側の判定は **`CUSTOM_DOMAIN_CERT_ARN` の有無のみで分岐**（ご提案通り）。
- 両方セットされている → `Distribution` に `domainNames` + `certificate: Certificate.fromCertificateArn(...)` を付与、Lambda env `CLOUDFRONT_DOMAIN = CUSTOM_DOMAIN` に
- 未設定 → 現状通り（default cf domain）

### setup2b 側の動き（デグレ最小の手順）
1. setup2b Phase B〜C 完了時点で .env に上記2つを追記（既に setup-state.json に持っている値の写し）
2. **以降 setup1b を再実行しても剥がれない**（再紐付けフェーズが事実上不要に）
3. 既存の Phase D-2「再紐付け」ボタンは**残す**（CDK env 経由が壊れた時の救済として価値あり）

### デグレ防止の最重要ポイント（route53 の $15 を踏ませないため）

**Route53 モードを実機テストせずに保証する戦略**として、以下を満たせば「external が動けば route53 も 99.9% 動く」と言えます：

1. setup2b コード内の **route53 用 attach 処理は external と完全に同じ関数を呼ぶ** ことをコードで保証する（既に `acm-cf-bind/attach` が共通化済みなら OK）。差分は「Route 53 にレコードを書くか」だけで、CDK 側に渡すパラメータ（`CUSTOM_DOMAIN` / `CUSTOM_DOMAIN_CERT_ARN`）に **モード依存のロジックを一切入れない**こと。
2. CDK 側の env 読み取りは **モード非依存**（外から見れば「ドメイン名と証明書 ARN の文字列ペア」でしかない）にする。
3. external でテストする際、setup-state.json の `mode` を一時的に `route53` に書き換えて Phase E（書換）まで通すドライラン（実 Route 53 を作らないユニットテスト相当）を追加してもよい。

これで「Route 53 経路特有のバグ」が入る面積はほぼ DNS レコード作成 API のみに限定されます。

## 4. WSL 配布イメージの容量削減

実測（環境）：
- `homepage/node_modules` = **1.4G**（うち `@next` 249M + `next` 172M + `googleapis` 111M + `@opentelemetry` 85M + `@firebase` 78M）
- node_modules = **583M**（うち `@next` 249M + `next` 172M）
- `homepage/.next` = 410M、.next = 761M
- `~/.npm` キャッシュ = 263M

合計で約 3.4GB の「再生成可能」物。配布イメージから以下を**削除した状態**で固めるのが効果大：

### 効果の大きい順（推奨）

| 対策 | 削減量目安 | リスク |
|---|---|---|
| **配布前に node_modules と .next を削除し、初回起動 `start.sh` で `npm ci` を走らせる** | 約 3GB | ネット接続必須・初回起動が長くなる |
| `~/.npm` キャッシュを削除 | 263M | なし |
| .next / .next のみ削除（node_modules は残す） | 約 1.2G | なし（dev/build で再生成） |
| tsconfig.tsbuildinfo 等のビルド成果物削除 | 数MB | なし |
| pnpm に切替えて hoist + hardlink で homepage/setup の重複（next 等）を共有 | 数百MB（next/@next が両方にあるので大きい） | 移行コスト中（Next.js + pnpm はOK） |
| homepage 側で `firebase` / `@firebase` / `googleapis` / `@google-cloud` 系を削減 | 〜300M | これらは `genkit` / `@genkit-ai` の transitive。AI機能を残すなら触れない |

### 一番おすすめ：「初回起動時 install」パターン

start.sh 冒頭に
```bash
[ -d ../node_modules ] || (cd .. && npm ci)
[ -d node_modules ]   || npm ci
[ -d ../.next ]       || (cd .. && npm run build)  # Lambdaに上げるならビルドはCDKデプロイ時で十分
```
を入れて、配布アーカイブからは両 node_modules と両 .next を除く。これで配布サイズ −3GB 級。`README` か WSL セットアップ手順に「初回起動はネット必須・5〜10 分」と書いておけば運用上問題なし。

### 妙案がなければ（=何もしないでよい範囲）
homepage 側の依存（firebase/googleapis 等）の手動削減は、genkit の transitive なので**やめた方がよい**です（バージョン整合の事故が起きやすい）。

## 1. Branch protection — `Add branch ruleset` を推奨

**why:** GitHub は「Classic branch protection」より「Rulesets」を新仕様として推している（複数ルール合成可、組織継承可、JSON エクスポート可）。今回は単一リポなので機能差は実質なしですが、新規作成なら Ruleset 一択でOK。

### 手順（Add branch ruleset → 以下のように設定）

1. **Ruleset Name**: `main protection`
2. **Enforcement status**: `Active`
3. **Target branches** → `Add target` → `Include default branch`（= main）
4. **Branch rules** で以下にチェック:
   - ☑ **Restrict deletions**（main 削除防止）
   - ☑ **Block force pushes**（履歴改ざん防止）
   - ☑ **Require a pull request before merging**
     - Required approvals: `0`（一人開発なので 0 でOK。CI だけ通せば merge 可）
     - ☑ Dismiss stale pull request approvals when new commits are pushed
   - ☑ **Require status checks to pass**
     - ☑ Require branches to be up to date before merging
     - **Add checks** で 5 つ追加（ジョブ名は security.yml の `name:` と一致）:
       - `Vitest (Route Handler & CDK 構造)`
       - `ESLint`
       - `npm audit (production high+)`
       - `Semgrep SAST (OWASP Top 10)`
       - `Gitleaks (秘密情報スキャン)`
       
       ※ 検索ボックスにジョブ名を入れると候補が出ます。一度 push して CI が走った後でないと候補に出ないので、すでに緑化済みの今ならOK。

5. **Create**

> ⚠ 注: 自分一人で main に直 push したい場合は「Bypass list」に自分を入れる、または「Require a pull request」のチェックを外す運用も可。完全に PR ベースで回したいなら入れたままで。

## 2. Dependabot（任意・推奨）

スクショを見ると **Dependency graph も Dependabot alerts も無効** の状態です。最低限以下だけ ON 推奨:

1. **Dependency graph** → `Enable`
2. **Dependabot alerts** → `Enable`（依存に CVE が出たら通知）
3. （任意）**Dependabot security updates** → `Enable`（自動 PR が来る。レビュー負荷を許容できるなら）

> Dependabot version updates（定期 PR）は本プロジェクトでは noisy になりがちなので**有効化非推奨**。security updates のみで十分。

## 3. その他オプション（やらなくてOK）

- **Private vulnerability reporting**: パブリックリポ向け機能なので、現状プライベートなら不要
- **CodeQL default setup**: 既に Semgrep を回しているので重複。スキップでOK
- **Secret Protection (Push protection)**: 既に gitleaks を CI で回しているので重複。スキップでOK

Affected versions
Patched version

>= 6.7.0, <= 6.14.1
6.14.2
Summary

The arrayLimit option in qs does not enforce limits for comma-separated values when comma: true is enabled, allowing attackers to cause denial-of-service via memory exhaustion. This is a bypass of the array limit enforcement, similar to the bracket notation bypass addressed in GHSA-6rw7-vpxm-498p (CVE-2025-15284).
Details

When the comma option is set to true (not the default, but configurable in applications), qs allows parsing comma-separated strings as arrays (e.g., ?param=a,b,c becomes ['a', 'b', 'c']). However, the limit check for arrayLimit (default: 20) and the optional throwOnLimitExceeded occur after the comma-handling logic in parseArrayValue, enabling a bypass. This permits creation of arbitrarily large arrays from a single parameter, leading to excessive memory allocation.

Vulnerable code (lib/parse.js: lines ~40-50):

if (val && typeof val === 'string' && options.comma && val.indexOf(',') > -1) {
    return val.split(',');
}

if (options.throwOnLimitExceeded && currentArrayLength >= options.arrayLimit) {
    throw new RangeError('Array limit exceeded. Only ' + options.arrayLimit + ' element' + (options.arrayLimit === 1 ? '' : 's') + ' allowed in an array.');
}

return val;

The split(',') returns the array immediately, skipping the subsequent limit check. Downstream merging via utils.combine does not prevent allocation, even if it marks overflows for sparse arrays.This discrepancy allows attackers to send a single parameter with millions of commas (e.g., ?param=,,,,,,,,...), allocating massive arrays in memory without triggering limits. It bypasses the intent of arrayLimit, which is enforced correctly for indexed (a[0]=) and bracket (a[]=) notations (the latter fixed in v6.14.1 per GHSA-6rw7-vpxm-498p).
PoC

Test 1 - Basic bypass:

npm install qs

const qs = require('qs');

const payload = 'a=' + ','.repeat(25);  // 26 elements after split (bypasses arrayLimit: 5)
const options = { comma: true, arrayLimit: 5, throwOnLimitExceeded: true };

try {
  const result = qs.parse(payload, options);
  console.log(result.a.length);  // Outputs: 26 (bypass successful)
} catch (e) {
  console.log('Limit enforced:', e.message);  // Not thrown
}

Configuration:

    comma: true
    arrayLimit: 5
    throwOnLimitExceeded: true

Expected: Throws "Array limit exceeded" error.
Actual: Parses successfully, creating an array of length 26.
Impact

Denial of Service (DoS) via memory exhaustion.
Suggested Fix

Move the arrayLimit check before the comma split in parseArrayValue, and enforce it on the resulting array length. Use currentArrayLength (already calculated upstream) for consistency with bracket notation fixes.

Current code (lib/parse.js: lines ~40-50):

if (val && typeof val === 'string' && options.comma && val.indexOf(',') > -1) {
    return val.split(',');
}

if (options.throwOnLimitExceeded && currentArrayLength >= options.arrayLimit) {
    throw new RangeError('Array limit exceeded. Only ' + options.arrayLimit + ' element' + (options.arrayLimit === 1 ? '' : 's') + ' allowed in an array.');
}

return val;

Fixed code:

if (val && typeof val === 'string' && options.comma && val.indexOf(',') > -1) {
    const splitArray = val.split(',');
    if (splitArray.length > options.arrayLimit - currentArrayLength) {  // Check against remaining limit
        if (options.throwOnLimitExceeded) {
            throw new RangeError('Array limit exceeded. Only ' + options.arrayLimit + ' element' + (options.arrayLimit === 1 ? '' : 's') + ' allowed in an array.');
        } else {
            // Optionally convert to object or truncate, per README
            return splitArray.slice(0, options.arrayLimit - currentArrayLength);
        }
    }
    return splitArray;
}

if (options.throwOnLimitExceeded && currentArrayLength >= options.arrayLimit) {
    throw new RangeError('Array limit exceeded. Only ' + options.arrayLimit + ' element' + (options.arrayLimit === 1 ? '' : 's') + ' allowed in an array.');
}

return val;

This aligns behavior with indexed and bracket notations, reuses currentArrayLength, and respects throwOnLimitExceeded. Update README to note the consistent enforcement.
